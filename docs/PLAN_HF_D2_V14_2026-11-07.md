## 1. 要做的两件事

### 1.1 少跑：S3 同键图的脊抽查

- 同键图的脊（`_same_graph_ridge`，v1.2 定义不变）按种子抽样：`_key(seed, "same_graph_sample", intent_id) < audit_fraction` 的照常派发 HS / HC，仍放在最后一组。
- 没抽中的记 `HS_skipped:same_graph_ridge`，HC 也不跑。它不是"无反应"，扫描与升级记录照常保留。
- 比例沿用冻结的 `audit_fraction`（b05 为 0.1），不新增数值。
- HS payload 的 `same_graph_ridge` 标签照旧；报告加 `same_graph_ridge: {sampled, settled, skipped, deferred}`，以及样本中的 HS 结局与候选数。样本出了候选就醒目列出：那说明这条规则在该体系不安全。

### 1.2 并行：HS / HC 按波次并行（异构）

照 `_run_scans` 的做法：

1. **按组分波次**：第一轮 → 第二轮 → 同键图的脊样本，组间严格先后，保持 v1.1–v1.3 的优先级。组内按升级顺序，每波最多 `wave_size` 项。
2. **派发**：波内每项照现在的办法先预留 `hs_cap`（HC 预留 `hc_cap`），预留失败就停止这一波；这一波一项都派不出去时，剩余项按现行原因记暂缓或跳过。没有新的跳过条件。
3. **执行**：`run_many([TaskJob...], backends.search_batch, max_active)`，HS / HC 共用常驻的批量求值器；每个任务有自己的账本（`run.task_ledger(cap)`），forward 照现行在派发时计费。
4. **结算**：波结束后，按输入顺序逐项 `settle`。HC 的判重（`_hf_duplicate`）也在结算循环里按顺序做，所以判重语义与串行完全相同；`trace_sides_ef` 在并行阶段只返回连接结果，不碰 `run.settled`。
5. **异构**：HC 依赖本波 HS 的结算结果。分两步做：
   - 第一步：每波先 HS、后这一波出候选的 HC，两次 `run_many`；
   - 第二步：流水线化，把第 k 波的 HC 和第 k+1 波的 HS 放进同一次 `run_many`。
   每步之间看测量结果再决定要不要做第二步。
6. **并发度**：沿用冻结的 `max_active` / `wave_size`（b05 为 4 / 16）。在 v1.4 之前，这两个值只用于扫描；v1.4 起也用于 HS / HC。

### 1.3 规则版本

`D2-HF-v1.4` = v1.3 + S3 + HS / HC 按波次并行；冻结开关 `same_graph_sample=True` 和 `hf_parallel=True`，都要求 v1.3。旧运行不追认；续跑旧运行的行为不变。

并行本身不改语义，但有两处行为会变，所以要算进规则版本：
- **额度用尽前的最后一波**：同时预留 W 个上限，能派出的项数可能比串行少，余下的项等下一波，不会被跳过。
- **数值**：批量求值与单结构求值在 fp32 下不逐位相同。

## 2. 测试（解析台，CPU）

解析台的批量求值是逐结构精确的，所以可以要求并行与串行逐项一致：

- **S3**：抽中的照常派发、没抽中的记 `HS_skipped:same_graph_ridge`；计数闭合；比例为 0 和 1 时分别等于"全跳过"和 v1.3。
- **并行 = 串行**：同一冻结输入下，v1.4（并行，`max_active` > 1）与 v1.4（`max_active` = 1）的 settle 序列、状态、候选几何、HC 判重结果逐项相同；外部计数 = 账本。
- **组间优先级**：额度只够一波时，后面的组不被派发。
- **续跑**：波中途 kill → resume，已付费用只付一次，已结算的不重跑。照 `test_d2_resume` 的做法，至少覆盖 HS 波中、HC 波中两处。
- **判重顺序**：同一波里两个 HC 连到同一个事件时，按输入顺序前一个是 `connected`、后一个是 `hf_duplicate`。
- **变异检验**：结算改成按完成顺序、判重放进并行阶段、组间不分先后、S3 不跳过。各应使至少 1 个测试失败。

## 3. 测量与冒烟（真实模型，183）

先量后建，测的量和对照都在动手前写定：

1. **基线**：v1.3（串行 HS / HC）跑一段 HS，同时每秒采样 `nvidia-smi` 的 GPU 利用率，记每个 HS forward 的墙钟。输入用 11-07 v1.3 验收的 22 + 15 项冻结括区（`midpoint_coarse_candidate_validate.py` 的项）。
2. **并行**：同样的项用 `run_many` 并行（`max_active` 4，以及 8 作对照），记 GPU 利用率、每个 forward 的墙钟、批大小（`run_many` 的 `batch_rounds`）、总墙钟。
3. **一致性**：两种方式的结局、候选身份（对称 RMSD、ΔE）按"结局与事件一致"比，不比逐位相同。不一致的项再各跑 2 次，区分 fp32 波动和并行的影响。
4. **D2 冒烟**：`run_b05_d2.py` 小规模（同 10-26 冒烟：1 姿态 12 意图），加 v1.4 开关，端到端一次，账目闭合。

加速比现在不知道，要先跑一小段才知道。扫描阶段已经在并行（`scan_many`，同样的 4 / 16），但没有记录过它的 GPU 利用率。

## 未确认（Claude 推断）

- 显卡很空、瓶颈在串行，是从"16 原子单结构 forward + 串行 HS"推出来的，整跑期间的 GPU 利用率没有测过（§3 第 1 步就是测这个）。
- 并行的收益要看 `run_many` 的协调开销与 HS 里的 CPU 部分（约束投影、BFGS / FIRE 更新、对齐）；HS 的 CPU 时间占比没有测。
- 并行任务共用批量求值器，计费方式与扫描相同（派发时按结构计 forward），与现行 `view_factory` 的计数应一致，要在解析台上核对。
- 用 `audit_fraction` 作抽样比例是借用已有数值；它原本是"从被筛掉的意图中抽查"的比例，两者用途相近，但不是为同键图的脊专门定的。
